# Dark Mode Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Implement account-synced Light, Dark, and System appearance on `feature/dark-mode`.
**Architecture:** Semantic CSS tokens follow a document-root theme. A tested state controller handles server synchronization independently of React; a provider binds it to authentication and browser events. The account database is authoritative, with an anonymous preference and startup cache for first paint.
**Tech Stack:** Existing React/TypeScript/Vite, Java/Spring Security/JPA/Flyway, Node test runner, Spring MockMvc.
**Spec:** `docs/superpowers/specs/2026-09-23-dark-mode-design.md`.

## Global Constraints

- Keep existing application workflows and user edits intact; no new production dependency.
- User explicitly requested implementation and a new branch; execute locally and provide progress updates.
- Database preference is `system`, `light`, or `dark`; authenticated principal determines ownership.
- Cross-device refresh on focus and every 60 seconds while visible; no automatic write replay.
- Preserve V1 migration; add V2 for both H2/PostgreSQL.

## Review Focus

- A response from account A must never change account B's theme (controller deferred-response test).
- A background GET must not override a newer choice (controller race test).
- Storage exceptions must not disable account persistence (cache/controller test).
- A failed PUT may have committed; retry is explicit and idempotent (controller failure/retry test).
- Login/logout and open application drafts must survive appearance changes (browser checks).
