# Recovery and rollout qualification

These procedures require an isolated rehearsal and an approved hosting configuration. The local Compose tests prove process restart, dependency failure and migration gating; they do not prove zone failover, point-in-time restore, RPO or RTO.

## Inventory before a release or restore

Record the tested source/image digests; Flyway versions/checksums; database service/version/topology; administrator/migrator/API/mail/export role privileges; database counts and representative owner-scoped records; outbox/job state/age and active leases; private bucket/lifecycle/encryption settings; current and decrypt-only outbox key IDs; secret-manager references; Redis session/admission namespace and serializer version; origin/cookie/proxy trust settings; connection ceilings including replacements. Store actual keys/credentials only in protected recovery storage. Database backups without the needed decrypt keys cannot recover encrypted queued mail.

Back up PostgreSQL using the hosting service's encrypted backups and continuous WAL/PITR when the RPO requires it. Verify backup retention and restore permissions. For local rehearsal, `pg_dump --format=custom` under a protected administrative environment creates a database archive; role definitions/ownership and key inventory are a separate protected administrative backup. Never echo passwords or commit archives, secrets, database files or bucket contents. Do not assume a successful backup job proves recoverability.

## Isolated database restore rehearsal

1. Create a new private database/cluster and a new empty bucket or isolated storage namespace. Label the rehearsal, record start time and restore point, and verify it differs from every active user endpoint/volume. Disable registration and block public traffic. Start no delivery workers yet.
2. Restore the backup/WAL to that new cluster using the documented service workflow. For a dump, restore the archived roles under administrator control and use `pg_restore --exit-on-error` against the new target. Inspect unexpected owners/roles rather than applying broad ownership reassignment. Do not run the fresh-database provisioner on restored tables.
3. Validate Flyway checksums and compatible migration order. Apply the explicit worker-role upgrade when needed, run the one-shot migrator/grants, then `verify-runtime.sql`. A missing role or failed grant blocks APIs/workers. Compare counts and sample values for users, applications, stages, preferences, deleted records, tokens and jobs with the backup inventory. Use fresh isolated role connections to verify prohibited DDL/account mutation remains denied.
4. Supply the compatible outbox decrypt key overlap, private object-storage access, and new environment-specific namespaces. Validate HTTP ownership, login, CSRF rotation, version conflict, undo and full CSV using synthetic rehearsal identities. Verify private output exists for retained READY jobs, or make unavailable/expired output explicitly unavailable through a reviewed recovery operation. Do not publish a dangling download as successful.
5. Keep delivery disabled until the operator resolves pending/SENDING leases and potential provider acceptance. Recovered mail can be redelivered with its stable Message-ID and the same single-use token. Repeated delivery must never mean repeated verification or password changes. Retain payloads/keys only within the recovery/retention window; remove them through bounded maintenance afterwards.
6. Rebuild/invalidate shared sessions deliberately after uncertain Redis restore/failover. A recovered session store must not resurrect acknowledged logout. Restored admission counters can lose recent restrictions: block or conservatively rate-limit admission during reconciliation, and measure actual fail-closed behavior. Do not silently switch to local sessions or an unbounded in-memory limiter.
7. Record time to usable validated service and the timestamp of the last restored acknowledged write. Compare measured loss/recovery with approved RPO/RTO. Only then prepare the endpoint switch for explicit deployment approval. Preserve the old target until the rollback window closes; never restore directly over an existing user database for testing.

## Expand, backfill, switch, contract

Use additive versioned migrations first. Provision least-privilege roles before grants; apply grants/migrations through a one-shot job and gate all dependent processes. Backfill in resumable bounded batches and measure locks, write amplification and pool wait. Deploy readers compatible with both versions, verify correctness, then switch traffic/features. Keep old columns/indexes/keys/serializer readers until all old API/worker versions and recovery windows have drained. A later contract migration removes them only after that inventory is verified. Never edit an applied migration.

Rolling deployment must reserve connection overlap and drain budget before launching replacements. Remove a draining API from hosted readiness routing before termination; preserve shared session/cookie/CSRF configuration. Nginx's local passive fail handling may expose a transient gateway failure; no failed mutation is replayed. Mail retries and exports remain fenced by the current lease. An old worker cannot complete a newer owner's job. API rollback is safe only while its schema, session format, DTOs and grants remain compatible; otherwise restore into a separate validated target before switching. Never "fix" rollback by granting runtime superuser rights.

## Hosted acceptance record still required

Specify provider/account, region/zones, public origin, budget, container limits/autoscaling, maximum rollout overlap, managed PostgreSQL synchronous failover/PITR policy, Redis persistence/TLS/failover policy, private storage lifecycle/encryption, SMTP limits, secrets source and approved SLO/RPO/RTO/retention. Prepare reviewable IaC after those inputs, before billable provisioning or public deployment.

Rehearse loss of an API, first zone and primary database instance; verify acknowledged routine writes survive synchronous failover. Exercise Redis failover with active sessions, quotas and acknowledged logout; no authentication fallback or logout resurrection is acceptable. Inject SMTP timeout, storage outage, pool exhaustion and a killed worker after provider acceptance/upload. Test deployment rollback and isolated PITR. The proposed disaster targets are RPO ≤5 minutes and RTO ≤60 minutes; no result is claimed until measured on the selected service configuration.

Run representative skew, successful-auth and shared-NAT flows, 1,500 total HTTP requests/s sustained, 2,000/s bursts and multi-hour soak under approved resources. Record achieved arrivals and dropped load, p95/p99, legitimate 429/503, browser render latency, heap/GC, pool wait/connection ceiling, Redis memory and queue/export/mail interference. Large 60-million/180-million fixtures are explicit qualification runs rather than daily CI. Optimize only a measured bottleneck; summary caches, replicas, search, broker, partitioning and sharding remain optional decisions with consistency and recovery tests.
